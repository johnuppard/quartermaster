# Quartermaster routing table (shipped)

This file ships with Quartermaster and is generic. Your own rows, tiers for your own skills and anything the daily self-review learns go in `ROUTING.local.md` next to it; local wins where the two overlap. Do not edit this file by hand on an installed copy; an update would overwrite it.

## Tiers (cost rank, most expensive first)

| Tier | Model | Use for | Never for |
|---|---|---|---|
| Fable | claude-fable-5-1 | Understanding an unclear request, splitting a new or large task, design and architecture decisions, arbitration when agents disagree or a check fails twice, escalations the user approved | Executing a known plan, data pulls, file edits, formatting, summaries, waiting for agents |
| Opus | claude-opus-5-5 | The foreman role, judgment with data, analysis and reports, text a client or the public reads, text in a second language, code that touches live systems, checking and editing before the user sees it, legal, money, brand | Bulk mechanical work, sweeps, lookups |
| Sonnet | claude-sonnet-5-5 | Executing a clear spec: file edits per plan, scripts, data pulls, searches, test runs, verifying Haiku work, first drafts of internal text, routine changes with an existing pattern | Final client-facing text, decisions, anything live without an Opus check |
| Haiku | claude-haiku-5-5 | Listing, grepping, classification, summarising logs, extracting fields from many files, checking mechanical done-criteria (file exists, line count, no forbidden character) | Writing anything a person reads as a deliverable, judgment of any kind |

Prices used by the scorecard are in `prices.json` (list prices, dated). Edit that file if yours differ.

## Task type → tiers

Ceiling = the highest tier a piece may step up to on its own when its agent returns ESCALATE or its verifier answers no. The row's ceiling is the default; the plan may lower it; only the user may raise it. Check = the tier of the separate agent that verifies the result (never the agent that did the work, never lower than it).

| Task type | Plan | Execute | Ceiling | Check |
|---|---|---|---|---|
| Text a client or the public reads (email, letter, proposal, post, page copy) | Opus | Opus, or the owning skill | Opus; Fable only after the user says yes | Opus checker + Opus editor |
| Report or analysis with figures | Fable if new, else Opus | Opus writes; Haiku and Sonnet pull data | Opus | Opus, figures against sources |
| Website, portal, CMS or app change (live) | Fable if new design, else Opus | Sonnet on a test copy first; Opus for the live rollout | Opus | Opus on the payload before, Opus as the end user after |
| Scripts, automation, scheduled jobs | Fable if new design, else Opus | Sonnet | Opus | Sonnet runs it; Opus reads the output |
| Audit or sweep over many files or records | Opus | Haiku finders; Sonnet verifiers | Finders Sonnet; verifiers Opus | Sonnet recount, loop until nothing new |
| Research | Opus | Sonnet searchers in parallel | Opus | Opus synthesis |
| Translation or second-language text | Opus | Opus for anything a client reads; Sonnet draft for internal text | Opus | Opus, native check |
| Ads: any change to a live campaign or spend | Opus | Owning skill, or Opus | Opus | Opus on the exact change, user's yes before anything live |
| CRM or bulk data change | Opus | Sonnet in dry-run first | Opus | Opus on the dry-run digest, user's yes before the live run |
| Contract, legal or compliance review | Opus | Opus, or the owning skill; never below Opus | Fable only after the user says yes | Opus |
| Meeting minutes or transcript work | Opus | Owning skill, or Sonnet draft | Opus | Opus |
| Monitoring, incident or bug investigation | Opus | Sonnet investigates; Opus diagnoses | Opus | Sonnet reproduces the fix |
| Building or changing skills, agents or jobs | Fable if new design, else Opus | Sonnet | Opus | Opus reads; Sonnet runs it |
| Sending, publishing, scheduling, spending (any) | Opus | The mechanical sender runs on Sonnet; the content comes from Opus | Opus | Opus reads the exact payload, user's yes, then send |
| Image or video generation | Opus | Owning skill, or Sonnet | Opus | User picks |
| Lookups, listings, status | none | Haiku | Sonnet | none, unless the result feeds a live change: then a Sonnet recount |

Rule for any row: a send, publish, spend, delete or live write is never executed by the agent that wrote the content, and never before the user's yes.

## Skills by tier

Each installed skill's `model:` line is the source of truth. `runtime/skill-models.json` is the approved snapshot; the daily self-review restores a line an update dropped and lists new skills in `ROUTING.local.md` with the tier this rule gives them:

- Mechanical or tool-wrapper skill → Sonnet.
- Writes text others read, decides, or touches money or legal → inherits the session (Opus).
- Fable → only when the user sets it by hand.

Plugin and marketplace skills that are not files on this machine are not controlled; treat them as Opus for judgment and client text, and say so in the plan.

## Cost rules

- Policy: a check one tier up costs less than redoing the piece on that tier, provided the check does not redo the work.
- Policy: one escalation of one piece costs less than a weak result the user has to send back. Never let a cheap agent try harder; escalate.
- Likely, measured by the scorecard over time: splitting pays when each piece is more than a few tool calls; a piece one agent finishes in ten calls is not split.
- True by construction: parallel agents save time, not tokens; each agent re-reads its inputs.
- The honest baseline is the session's normal model (Opus), not Fable. The scorecard shows both.
